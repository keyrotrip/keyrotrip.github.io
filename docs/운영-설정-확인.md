# 운영 설정 확인 · 바꿀 것 (2026-10-16)

이 문서의 내용은 **아직 아무것도 적용하지 않았습니다.** 코드는 저장소에만 고쳐 두었고,
운영(Supabase 대시보드 · GitHub 저장소 설정)은 이 순서대로 사람이 직접 해야 합니다.
비밀값은 이 문서·로그·커밋 어디에도 적지 마십시오.

각 항목은 둘로 나눴습니다.
- **확인 필요** — 저장소만 봐서는 알 수 없는 것. 추측으로 «괜찮다» 하지 않았습니다.
- **할 일** — 코드 변경과 짝이 맞아야 하는 운영 작업. 순서가 있으면 순서대로.

## 1. push 함수 인증 (`supabase/functions/push/index.ts`)

### 무엇을 고쳤나
`allowed()` 가 «증명이 아닌 것»을 서버 열쇠로 받았습니다.
- `Bearer sb_secret_` 로 **시작하기만** 하면 통과
- 레거시 JWT 의 payload 에 `role: service_role` 이 **적혀만** 있으면 통과 — 서명을 안 봤습니다

옛 코드에 꾸민 값 두 개를 넣어 보니 둘 다 `ok:true` 였습니다(로컬, 운영에는 안 보냄).

이제 받는 길은 둘이고, 둘 다 **비밀값과 글자까지 같음**(시간이 일정한 비교)입니다.

| | 머리 | 견주는 값 | 비고 |
|---|---|---|---|
| **A (정한 방식)** | `x-cron-secret` | 함수 비밀값 `PUSH_CRON_SECRET` | 스케줄러 전용 열쇠 |
| B (옮기는 동안) | `Authorization: Bearer …` | 함수에 자동으로 들어오는 `SUPABASE_SERVICE_ROLE_KEY` | 지금 스케줄러가 쓰는 길 |

### 확인 필요
1. **push 함수의 게이트웨이 JWT 검사(verify_jwt)가 켜져 있는가.**
   저장소에 `supabase/config.toml` 이 없고 배포는 대시보드에서 합니다. 대시보드 →
   Edge Functions → push → 설정에서 «Enforce JWT verification(또는 Verify JWT)» 상태를 보십시오.
   - 켜져 있었다면: 꾸민 JWT 는 게이트웨이에서 이미 막혔을 것입니다. 다만 `sb_secret_…` 꼴은
     JWT 가 아니라 게이트웨이가 어떻게 다루는지 확인이 필요합니다.
   - 꺼져 있었다면: 옛 코드는 **누구나** 알림을 쏠 수 있었습니다.
2. **GitHub Secrets 의 `SUPABASE_SERVICE_KEY` 가 함수의 `SUPABASE_SERVICE_ROLE_KEY` 와 글자까지 같은가.**
   옛 주석에 «종류가 달라 403 이 났다»는 기록이 있습니다. 다르다면 **B 로는 통과하지 못하므로**
   이 판의 함수를 올리는 순간 알림이 멈춥니다. → 아래 «할 일»의 1·2 를 **먼저** 하십시오.
   (값을 화면에 띄워 견주지 말고, 길이만 보거나 A 로 옮기는 것으로 해결하십시오.)

### 할 일 (순서대로)
1. 긴 무작위 값을 하나 만듭니다(예: 비밀번호 관리자에서 40자 이상). 어디에도 붙여 두지 마십시오.
2. Supabase → Edge Functions → **Secrets** 에 `PUSH_CRON_SECRET` = 그 값.
3. GitHub 저장소 → Settings → Secrets and variables → Actions 에 `PUSH_CRON_SECRET` = **같은 값**.
4. 고친 `push.yml` 이 올라간 뒤(커밋·푸시), 고친 `push/index.ts` 를 대시보드에 붙여 배포.
5. Actions → push-reminders → «Run workflow» 로 한 번 돌려 `HTTP 200` 을 확인.
   403 이면 답의 `받은키` 를 보십시오(열쇠 값은 답에 안 실립니다).

> 어느 순서로 넣어도 알림이 멈추지 않게 짰습니다 — 함수에 비밀값이 없으면 머리를 무시하고
> B 로 판단하고, 스케줄러가 머리를 안 보내면 B 로 갑니다. 다만 2번의 «글자까지 같은가»가
> 아니라면 B 가 실패하므로, A(2·3번)를 먼저 넣는 것이 안전합니다.

### 그 뒤(선택)
A 로 옮긴 것이 확인되면, 게이트웨이가 요구하지 않는 한 스케줄러가 `service_role` 키를 들고 있을
이유가 없습니다. verify_jwt 가 켜져 있으면 Authorization 에는 공개 키(anon)를 두고 A 로만 증명하는
방식도 가능합니다 — 이건 운영 결정이라 코드는 B 를 남겨 두었습니다.

### 시험
`deno test --node-modules-dir=none --allow-env --allow-read supabase/tests/push_auth_test.ts` — 11개.
꾸민 JWT · `sb_secret_` 접두사가 막히는지, A·B 와 옮기는 동안의 조합이 맞게 판단되는지 봅니다.

## 2. chat 함수의 바깥 요청 (`supabase/functions/chat/index.ts`)

### 무엇을 고쳤나
사용자가 준 주소를 서버가 대신 받는 세 자리(블로그 본문 · 블로그 안 iframe · 지도 단축 주소)가
**검사 없이** 받았습니다.
- 블로그: 아무 주소나 `redirect:'follow'` 로 끝까지 따라감 → 내부 주소로 바로, 또는 바깥 주소가
  내부로 리다이렉트
- iframe: 남이 쓴 페이지가 정한 주소를 그대로 받음
- 지도: 주소 «어디에든» `goo.gl` 글자가 있으면 받음 — `https://maps.google.evil.com/?goo.gl` 를
  지도로 보고 받으러 갔음(옛 코드에 넣어 확인, 로컬)
- 크기: `Content-Length` 머리만 믿고 `res.text()` 로 끝까지 받음

이제 셋 다 `안전요청` 하나를 지납니다: 주소 꼴 검사 → DNS 로 풀어 내부 대역이면 막기 →
리다이렉트를 한 단계씩 다시 검사(최대 4번) → 처음부터 끝까지 한 번의 제한 시간 → 본문을
흘려 받으며 상한에서 끊기 · 글이 아닌 것은 안 받기.

### 확인 필요
1. ✅ **확인됨(2026-10-16): 된다.** 목록에 없는 japan-guide.com 링크를 실제로 읽었습니다(TIMING `글자 4797` · links 1.0초).
   아래는 확인 전에 적어 둔 갈래입니다.
   **Supabase Edge Runtime 에서 `Deno.resolveDns` 가 되는가.**
   - 된다면: 모든 공개 블로그를 받되, 내부로 풀리는 이름은 막습니다.
   - 안 된다면: 코드는 **알려진 블로그·지도 이름**(naver · tistory · brunch · velog · blogspot ·
     wordpress · medium · google 지도 · goo.gl)만 받고 나머지 링크는 «못 읽었어요»가 됩니다.
     배포 뒤 개인 블로그 링크 하나로 확인하십시오. 함수 로그에 오류 문구는 안 남깁니다(사용자
     화면에는 «링크를 못 읽었어요»).
2. (위험 크기 판단용) Edge 함수 안에서 `169.254.169.254` 같은 메타데이터 주소가 실제로 닿는지는
   플랫폼 사정입니다. 코드로 막았으므로 결과와 상관없이 막히지만, 옛 판이 얼마나 위험했는지는
   이것에 달려 있습니다.

### 남는 위험 (코드로 못 막음)
- **DNS 재바인딩**: 우리가 이름을 푼 «직후» 그 이름의 IP 가 바뀌면 fetch 가 다시 풀 때 다른 곳으로
  갈 수 있습니다. Deno 의 fetch 에 «이 IP 로만 연결»을 지정할 길이 없습니다. 완전히 막으려면
  바깥 요청을 고정 IP 프록시(내부망에 못 닿는 곳)를 거치게 하는 운영 구성이 필요합니다.

### 할 일
1. `chat/index.ts` 를 대시보드에 **한 파일 그대로** 붙여 배포(새 파일·새 비밀값 없음).
2. 배포 뒤: 네이버 블로그 링크 하나 · 구글 지도 단축 주소(maps.app.goo.gl) 하나로 «링크를 읽었어요»를 확인.

### 시험
`deno test --frozen --node-modules-dir=none --allow-env --allow-read supabase/tests/chat_safe_fetch_test.ts`
— 16개, **모의 fetch·모의 DNS 만** 씁니다(바깥으로 안 나감).
(1차 때는 타입 오류 12개 때문에 `--no-check` 로 돌렸습니다. 2차에서 그 12개를 고쳐 이제 타입 검사까지 합니다 — 「8」.)

### 같이 본 것 (고치지 않음 — 범위 밖)
`city-photos` 함수의 옛 꼴(주소 문자열 하나) 경로는 받을 곳을 못박지 않았습니다(새 꼴은 Pexels·
위키미디어로 못박음). 서버에서 `is_admin()` 으로 관리자만 들이므로 위험은 낮지만, 같은 허용 목록을
옛 꼴에도 거는 것이 맞습니다.

## 6. 검사를 통과한 커밋만 배포 (`.github/workflows/check.yml` 의 `deploy` 일)

### 무엇을 바꿨나
지금은 Pages 원본이 **브랜치**라서 push 하는 순간 검사와 상관없이 올라갑니다(검사는 «올라간 뒤 빨간불»).
`deploy` 일을 더했습니다: `check` 일이 통과해야만, 그 **같은 커밋**(`github.sha`)의 파일 그대로를
(`git archive` — 저장소에 올라 있는 814개 그대로) Pages 에 올립니다.
- 검사하는 사이에 main 이 더 나아갔으면 옛 판은 올리지 않습니다(옛 판이 새 판을 덮는 일 방지).
- 올리기 직전에 `tools/frozen.pl` 을 한 번 더 봅니다 — 앱 주소·manifest `id:"/"`·`start_url:"."`·
  로그인 저장 이름 `t2-auth`·초대 링크 `?join=` 은 파일이 같으므로 달라지지 않습니다.
- 로컬에서 `git archive HEAD` 로 같은 단계를 흉내 내 보니 814/814 파일, 필수 파일·frozen 다 그대로였습니다.

**이 파일을 올려도 아무것도 안 바뀝니다.** 저장소 변수 `PAGES_FROM_ACTIONS` 가 `true` 가 아니면
`deploy` 일은 건너뜁니다.

### 확인 필요
1. 지금 Pages 설정: 저장소 → Settings → Pages → Build and deployment → Source 가
   «Deploy from a branch»(main / root)인지. (저장소만 보고는 모릅니다.)
2. 사용자 지정 도메인이 있는지(지금은 없다고 기억하지만 확인). 있으면 Actions 배포에서도
   같은 화면의 Custom domain 칸이 유지되는지 봅니다.
3. 저장소의 `github-pages` 환경(Environments)에 «배포 가능한 브랜치» 제한이 있으면 main 이 들어 있는지.

### 켜는 순서 (사람이 직접)
1. 고친 `check.yml` 을 커밋·푸시 → Actions 에서 `check` 가 초록인지 확인(`deploy` 는 «skipped»).
2. Settings → Secrets and variables → Actions → **Variables** 에 `PAGES_FROM_ACTIONS` = `true`.
3. **바로 이어서** Settings → Pages → Source 를 «GitHub Actions» 로.
   (2와 3 사이에 push 하면 그 판은 브랜치 방식으로 올라가고 deploy 일은 실패할 수 있습니다 — 해는 없지만 빨간불.)
4. Actions → check → «Run workflow»(main) 로 한 번 돌려 `deploy` 가 초록, 사이트가 그대로 뜨는지.
5. 사이트에서 확인: 첫 화면이 뜨는가 · 하단 판 번호가 방금 커밋의 판인가 · 홈 화면 앱이 다시 담기를 요구하지 않는가.

### 되돌리기
Settings → Pages → Source 를 «Deploy from a branch» 로 되돌리고 변수를 지웁니다. 파일은 그대로 둬도 됩니다.

### 남는 위험
- 검사가 빨가면 **올라가지 않습니다** — 급한 고침도 검사를 통과해야 나갑니다. 검사를 빼서 통과시키지 마십시오.
- 쓰는 Actions(`actions/*`, `denoland/setup-deno`)는 판 번호(@v4 등)로만 못박았습니다. 더 단단히 하려면
  커밋 SHA 로 못박는 것이 좋습니다(SHA 는 GitHub 에서 직접 확인해 넣을 것 — 여기 지어 적지 않았습니다).

## 7. AI 요청의 시간·입력 상한, DB 실패, 요청별 설정 (`supabase/functions/chat/index.ts`)

### 무엇을 고쳤나 (코드에서 확인한 문제)
| 문제 | 전 | 후 |
|---|---|---|
| 모델 설정 | 전역 변수 `activeModel` — 동시에 온 요청끼리 섞임 | 요청 안의 `모델`. 옛 코드로 시험을 돌려 **A 요청이 B 의 모델로 나가는 것**을 재현했고, 새 코드는 통과 |
| 요청 전체 시간 | 없음 | 120초 마감. 남은 시간이 3초 미만이면 새로 부르지 않음 |
| Gemini 한 번 | 대화·초안·불러오기는 제한 없음 | 60초(장소 45초·주소 30초는 그대로), 마감과 작은 쪽 |
| Tavily 한 번 | 제한 없음 | 12초, 마감과 작은 쪽. 모자라면 부르지 않음(크레딧 안 나감) |
| 입력 | 글 길이 제한 없음, 모양 검사 없음 | 대화 6,000자·불러오기 9,000자(화면은 8,000자)·지도 2,000자. `mode`·`trip_id`(uuid)·`message`(글) 모양 검사. 본문 9.5MB 넘으면 413(길이 머리 없이 흘려 보내도 받는 중에 끊음) |
| `ai_take`(사용량) 실패 | DB 오류 글을 사용자에게 그대로 | 멈추고 쉬운 말 + 문의 번호(`ref`). 까닭은 로그에만 |
| 여행·구간·일정 읽기 실패 | «(없음)»으로 답함 → «일정이 없네요» 같은 틀린 답 | 503 «여행 자료를 지금 못 읽었어요» |
| 없는(남의) 여행 | 여행 없이 답함 | 404 |
| 지출·일행·예약·담은 곳·준비물·취향·별점·대화기록 실패 | «(없음)» | 그 칸에 «못 읽었다 — 없다고 말하지 마라»를 적어 AI 에 줌. 대화기록은 «앞 대화를 가리키면 되묻기» |
| 설정(app_settings) 실패 | 조용히 기본값(검색 켬) | 로그에 남기고 기본 모델, **웹 검색은 끈 것으로**(돈 드는 쪽을 안전하게) |
| AI 비상 스위치(public_flags) 실패 | 조용히 켬 | 그대로 켬(앱을 멈추지 않음 — 위 ai_take 가 한도를 셈). 로그에는 남김 |
| 예상 못 한 예외 | 오류 글 그대로 | 쉬운 말 + `ref`. 로그에 `[ref] 단계별 시각` |
| supabase 클라이언트 | 요청마다 둘이 갱신 타이머(setInterval)를 켜고 안 끔 | `persistSession/autoRefreshToken:false` (Supabase 가 서버에 권하는 설정). 시험이 잡음 |

함수 파일 하나로 배포하는 방식은 그대로입니다(새 파일·새 비밀값 없음). 시험이 부를 수 있게
`처리`(요청 처리)·`callGemini`·`webSearch`·`readLinks` 를 내보냈을 뿐 하는 일은 같습니다.

### 확인 필요 (운영에 따라 달라지는 것)
1. **함수의 실제 시간 한도.** 코드 주석의 «150초»는 2026-09-28 실측입니다. 요금제를 바꿨거나 한도가
   달라졌으면 `요청예산ms`(120초)를 맞추십시오. 화면은 대화 90초(사진 150초)에서 포기합니다 — 서버가
   그보다 늦게 끝나면 사용자에겐 «시간 초과»로 보입니다(예전과 같음).
2. **화면에 `ref` 를 보여 줄지.** 지금 화면은 `error` 글만 띄웁니다. 문의 번호까지 보이게 하려면 화면 수정이
   필요합니다(이번엔 안 함). 로그에서 번호로 찾을 수는 있습니다: 함수 로그에서 `[번호]` 로 검색.
3. **같은 설정(`persistSession:false` 등)을 `city-photos`·`delete-me`·`push` 에도.** 같은 타이머가 요청마다
   켜질 수 있습니다. 이번 범위(chat)에서는 고치지 않았습니다.

### 배포
`chat/index.ts` 를 대시보드에 한 파일 그대로 붙여 배포 → 앱에서 대화 한 번 · 일정 초안 한 번 · 불러오기 한 번 ·
표 넣기(장소 이름 짓기) 한 번이 예전처럼 되는지. 함수 로그에 `TIMING` 줄이 찍히는지.

### 시험
`deno test --frozen --node-modules-dir=none --allow-env --allow-read supabase/tests/chat_handler_test.ts`
— 18개. Supabase·Gemini·Tavily 를 **가짜 fetch** 로 흉내 냅니다. 운영으로 아무것도 안 나갑니다.

## 10. 서버 함수 자동 배포 — «검사한 코드·의존성 = 배포한 것» (2026-10-16 준비, 아직 꺼짐)

### 왜
지금은 함수 파일을 대시보드에 **붙여 넣어** 배포합니다. 붙여 넣은 글자가 검사한 커밋과 같은지,
의존성(supabase-js)이 시험한 판인지 보장할 길이 없습니다(붙여 넣는 순간 `@2` 의 최신판을 받음).

### 준비해 둔 것(켜기 전에는 아무것도 안 바뀜)
- `supabase/config.toml` — 네 함수의 입구 검사(verify_jwt)를 **끔**으로. CLI 는 값이 없으면 «켬»으로 배포하는데,
  push 는 예약(pg_cron)이 로그인 표 없이 부르므로 켜지면 알림이 멈춥니다. 네 함수 모두 스스로 인증합니다(파일 머리말).
- 의존성 판 못박기: `supabase-js@2` → `@2.118.0`(시험한 판). 다음 배포부터 적용.
- `check.yml` 의 `deploy-functions` 일: check 통과 → 함수 파일이 바뀐 push 에서만 → `supabase functions deploy`(CLI 2.119.0).

### 켜는 순서(사람이 직접 — 승인 뒤)
1. Supabase → 오른쪽 위 계정 → **Access Tokens** → 새 토큰(이름 예: github-deploy). 값은 어디에도 적지 말 것.
2. GitHub → Settings → Secrets and variables → Actions
   - **Secrets**: `SUPABASE_ACCESS_TOKEN` = 1번 값
   - **Variables**: `SUPABASE_PROJECT_REF` = 프로젝트 주소의 앞부분(`https://<여기>.supabase.co`)
   - **Variables**: `FUNCTIONS_FROM_ACTIONS` = `true`
3. Actions → check → «Run workflow»(main) → `deploy-functions` 가 초록인지.
4. 확인: 함수 로그 · 앱에서 AI 대화 한 번 · SQL `select status_code from net._http_response order by created desc limit 3;` 이 200.
5. 그 뒤로는 대시보드에 붙여 넣지 않습니다(붙여 넣으면 저장소와 달라짐).

### 되돌리기
Variables 의 `FUNCTIONS_FROM_ACTIONS` 를 지우거나 false. 대시보드 붙여 넣기로 돌아갑니다.

### 남는 것
- 접근 토큰은 **계정 전체 권한**입니다(Supabase 가 프로젝트별 토큰을 아직 안 줌). GitHub Secrets 에만 두십시오.
- CLI 배포가 deno.lock 의 해시까지 지키는지는 확인하지 못했습니다 — 판은 import 주소에 못박아 두었습니다.
